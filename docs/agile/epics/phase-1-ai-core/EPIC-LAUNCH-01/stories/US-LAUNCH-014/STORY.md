## Story

*As a* new user who signs up with an email address and password
*I want* to receive a verification email immediately after registration and have my email address confirmed via a link
*So that* the product does not accumulate accounts with typo'd or fake email addresses that will later fail to receive billing-critical and security-sensitive transactional email (receipts, dunning notices, password resets).

---

## Acceptance Criteria

- [ ] **AC1:** When `POST /api/v1/auth/register` completes successfully for a new local email/password account, `EmailService.send()` is called exactly once with: `to` set to the new user's email address; `subject` containing the word "verify" (case-insensitive); and `html` or `text` body containing a URL of the form `{frontendUrl}/auth/verify-email?token={rawToken}` where `rawToken` is a 64-character lowercase hex string generated by `crypto.randomBytes(32).toString('hex')`. The raw token is never stored; only its SHA-256 hash (`crypto.createHash('sha256').update(rawToken).digest('hex')`) is persisted in `EmailVerificationToken.tokenHash`.

- [ ] **AC2:** After `POST /api/v1/auth/register` completes, exactly one `EmailVerificationToken` row exists for the new user with: `userId` matching the created user's id; `tokenHash` = SHA-256 of the raw token; `expiresAt` = 24 hours after creation (`Date.now() + 24 * 60 * 60 * 1000`); `usedAt` = null. If the Prisma insert for the `EmailVerificationToken` row throws (e.g. transient DB error), the error is caught and swallowed — the registration response still returns HTTP 201 with the new user and JWT token.

- [ ] **AC3:** The `User` model in `api/prisma/schema.prisma` has the field `emailVerified Boolean @default(false)` and the nullable field `emailVerifiedAt DateTime?`. The `register()` response body includes `user.emailVerified = false`. The `login()` response body includes `user.emailVerified` reflecting the user's current value in the database at the moment of login.

- [ ] **AC4:** `POST /api/v1/auth/verify-email` with body `{ "token": "<rawToken>" }` where the token's SHA-256 hash matches a `EmailVerificationToken` row that has `usedAt = null` and `expiresAt` in the future: returns HTTP 200 with `{ "verified": true }`; sets `User.emailVerified = true` and `User.emailVerifiedAt = now()` via a Prisma update; sets `EmailVerificationToken.usedAt = now()` via a Prisma update.

- [ ] **AC5:** `POST /api/v1/auth/verify-email` returns HTTP 400 in each of the following cases, with no mutation to `User` or `EmailVerificationToken`: (a) the SHA-256 hash of the submitted token does not match any row in `EmailVerificationToken`; (b) the matching row has `expiresAt` earlier than `new Date()` (expired); (c) the matching row has `usedAt` not null (already used).

- [ ] **AC6:** `POST /api/v1/auth/resend-verification` (requires a valid `Authorization: Bearer <jwt>` header — HTTP 401 if absent or invalid): (a) if the authenticated user's `User.emailVerified = true` in the database, returns HTTP 200 with `{ "alreadyVerified": true }` and calls neither `emailVerificationToken.create` nor `EmailService.send()`; (b) if `User.emailVerified = false`, deletes all existing `EmailVerificationToken` rows for the user where `usedAt IS NULL`, creates a new `EmailVerificationToken` row with the same shape as AC2, calls `EmailService.send()` exactly once, and returns HTTP 200 with `{ "sent": true }` regardless of the `EmailService.send()` return value or any thrown error.

- [ ] **AC7:** When a new `User` record is created inside `googleLogin()` in `auth.service.ts` (the branch where neither `prisma.user.findUnique({ where: { googleId } })` nor `prisma.user.findUnique({ where: { email } })` returns an existing record), the `prisma.user.create()` call includes `emailVerified: true` in its `data` object. No `EmailVerificationToken` row is created for Google OAuth signups and `EmailService.send()` is not called as part of the Google OAuth login path.

- [ ] **AC8:** When a logged-in user whose `user.emailVerified === false` (read from `localStorage.auth_user`, which is set by `AuthProvider.login()`) navigates to any route rendered via `AppLayoutWithHeader` in `App.tsx` — `/templates`, `/my-designs`, or `/account` — a banner component (`EmailVerificationBanner`) is rendered between the `<AppHeader />` and the `<main>` region. The banner contains text that includes the phrase "verify your email" and a button labeled "Resend verification email". Clicking the button calls `POST /api/v1/auth/resend-verification` (with the JWT from `localStorage.auth_token`) and displays a success message on `{ sent: true }` or `{ alreadyVerified: true }`. When `user.emailVerified === true` (or `user` is null), the banner renders nothing (`null`). No product action — infographic generation, template browsing, design editing, account settings — is disabled or blocked for unverified users.

- [ ] **AC9:** The public route `/auth/verify-email` is registered in `App.tsx` (Wouter `<Route>`) and renders `VerifyEmailPage`. On mount, `VerifyEmailPage` reads the `token` query parameter from the URL using Wouter's `useSearch()` and immediately calls `POST /api/v1/auth/verify-email` with `{ token }`. On HTTP 200 (`{ verified: true }`): displays a success state containing the word "verified" and a link or button that navigates to `/auth`. On HTTP 400 or network error: displays an error state informing the user the link is invalid or expired, with a prompt to sign in and request a new link. If the `token` query parameter is absent from the URL: displays the error state immediately without making an API call.

- [ ] **AC10:** The `EmailVerificationBanner` component renders without horizontal overflow at 375px viewport width. `VerifyEmailPage` renders without horizontal overflow at both 375px and 1440px viewport widths.

- [ ] **AC11:** Unit tests exist in `api/tests/auth/email-verification.spec.ts` (mock-based, no real DB) covering: (a) `register()` — `EmailService.send` mock is called once; `prisma.emailVerificationToken.create` mock is called with `tokenHash` (a 64-char hex string), `userId`, `expiresAt` approximately 24h from now, `usedAt` undefined/absent; (b) `verifyEmail()` with a valid token mock — `prisma.user.update` called with `{ emailVerified: true }` and `prisma.emailVerificationToken.update` called with `{ usedAt: expect.any(Date) }`; (c) `verifyEmail()` with an expired token mock — `BadRequestException` thrown, no Prisma update called; (d) `verifyEmail()` with a used token mock (`usedAt` not null) — `BadRequestException` thrown, no Prisma update called; (e) `resendVerification()` for a user with `emailVerified: true` — returns `{ alreadyVerified: true }`, `EmailService.send` mock never called; (f) `resendVerification()` for a user with `emailVerified: false` — `emailVerificationToken.deleteMany` called, `emailVerificationToken.create` called, `EmailService.send` mock called once.

## Out of Scope

- Blocking any product feature (infographic generation, template browsing, canvas editor, account settings, usage dashboard) behind email verification — this story is the soft/non-blocking implementation; `emailVerified` is a trust signal only.
- Re-send rate limiting or throttle policy beyond the simple "delete prior unused tokens before creating a new one" approach — complex rate limiting for the verification resend endpoint is a later story.
- Email verification for Google OAuth accounts — Google-authenticated users arrive with a Google-verified email and are marked `emailVerified: true` at account creation; no additional verification step is added for the OAuth path.
- Any change to the `PasswordResetToken` model, the password reset service methods (`forgotPassword`, `resetPassword`), or their DTOs (`ForgotPasswordDto`, `ResetPasswordDto`) — this story introduces a parallel, independent token type that must not disturb the existing reset flow.
- Showing the `EmailVerificationBanner` in the Editor (`/editor`) or Usage Dashboard (`/usage`) — those routes do not use `AppLayoutWithHeader` and are a separate enhancement.
- Email address change verification (re-verifying after a user updates their email in account settings) — the account page has no email-change UI today; that is a future story.
- A "check your email" interstitial page rendered immediately after registration — the registration response already redirects the user to the app; the banner (AC8) is the nudge mechanism.
