## Story

*As a* real-estate agent
*I want* each listing stored as a Property record on the server that my designs reference
*So that* two designs pointing at the same flat always show the same facts, and I never retype a listing

---

## Acceptance Criteria

- [ ] **AC1 [happy-path]:** `api/prisma/schema.prisma` gains a `Property` model: `id` (cuid PK), `organizationId` (required FK to `Organization`, `onDelete: Cascade`, `@@index`), `type` (default `"residential"`), `headline` (default `""`), `price` (String, default `""`), `beds` (Int, default 0), `baths` (Int, default 0), `sqft` (String, default `""`), `address` (default `""`), `description` (default `""`), `features` (String[], default `[]`), `locale` (default `""`), `photoRefs` (String[], default `[]`), `status` (default `"active"`), `createdAt`, `updatedAt`. `Organization` gains `properties Property[]`; `Infographic` gains `propertyId String?` with a `property Property?` relation and `@@index([propertyId])`. The migration is generated by `prisma migrate dev` and `prisma migrate deploy` applies it cleanly.
- [ ] **AC2 [happy-path]:** `POST /api/v1/properties` (JWT) accepts the optional fields above, creates a Property with `organizationId` from `req.user.organizationId || req.user.id` — never from the body — and returns 201 with `id`, `organizationId` and the saved fields.
- [ ] **AC3 [happy-path]:** `GET /api/v1/properties` (JWT) returns 200 with an array in which every item's `organizationId` is the caller's; no other organization's Property appears.
- [ ] **AC4 [happy-path]:** `PUT /api/v1/properties/:id` (JWT) updates only the fields present in the body on a Property the caller's organization owns and returns 200 with the full updated record including `updatedAt`. A body containing `id`, `organizationId`, `createdAt` or `updatedAt` is rejected with 400 by the global `forbidNonWhitelisted` validation (none of them is on the DTOs); ownership never comes from the body.
- [ ] **AC5 [security]:** `GET` and `PUT /api/v1/properties/:id` return 404 with no Property data when the id exists but belongs to another organization.
- [ ] **AC6 [security]:** Every route that reaches `DesignsService.save()` — `POST /api/v1/designs`, `PUT /api/v1/designs/:id`, `POST /api/v1/canvas-templates` and `PUT /api/v1/canvas-templates/:id` — returns 404 when given a `propertyId` belonging to another organization, and writes nothing (a following `GET` returns the previous `propertyId`). The check lives once, in `save()`. Covered by new cases in `api/tests/designs/designs.service.spec.ts`: other-org `propertyId` on create and on update → `NotFoundException`, `infographic.create`/`update` not called; own-org `propertyId` → saved.
- [ ] **AC7 [happy-path]:** `GET /api/v1/designs` and `GET /api/v1/designs/:id` include `propertyId: string | null` on every design object.
- [ ] **AC8 [rollback]:** After the migration, every pre-existing `Infographic` row has `propertyId = null`, `GET /api/v1/designs` returns the same number of designs as before, and no `canvasData` is altered.
- [ ] **AC9 [error-path]:** All four Property endpoints return 401 without a valid Bearer token.

## Out of Scope

- `DELETE /api/v1/properties/:id` — deferred until a removal UI exists
- `GET /api/v1/properties/:id/designs` — not needed by US-PROP-006
- Structured price fields (`amount`, `currency`, `transaction`, `rentalPeriod`) — US-PROP-002
- Any client-side change (`usePropertyStore`, `EditorLayout`, My Properties page) — US-PROP-006
- Changing the existing `userId`-only scoping on `GET /api/v1/designs` — separate debt
