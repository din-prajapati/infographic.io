## 4. Vitest module-load ordering quirk (and fix)

After writing the tests, the 4 orchestrator + processor tests passed, but both UsageLimitService tests failed with:

```
TypeError: Cannot read properties of undefined (reading 'PENDING')
at UsageLimitService.resolveEffectiveTier usage-limit.service.ts:168
```

Root cause diagnosis: when this test file imports `AiOrchestrator` (which imports `PrismaService` which imports `PrismaClient` from `@prisma/client`) alongside `UsageLimitService` (which imports `SubscriptionStatus` from `@prisma/client`), Vitest's module loading order causes `SubscriptionStatus` to be `undefined` in the test file's module instance. The existing `usage-limit.service.spec.ts` tests do NOT exhibit this because they don't import the AI service modules.

Verified the existing usage-limit spec tests pass in isolation (7/7) — so the production code is not broken, only the module context in my combined test file was affected.

Fix: added a passthrough `vi.mock('@prisma/client', async (importOriginal) => importOriginal())` at the top of the test file. This tells Vitest to load the real `@prisma/client` implementation while registering it in the mock registry, ensuring consistent resolution when multiple service files share the same module. Does not mock any behavior — purely a load-order fix. After this, all 6 tests passed.
