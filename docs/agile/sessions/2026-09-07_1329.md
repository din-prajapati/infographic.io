## 1. Product analysis — Quick Generate vs AI Chat

Verified against code, not assumed.

**Both surfaces are the same engine.** `RightSidebar.tsx:394` and `AIChatBox.tsx:815` both call `generationsApi.generate` → `POST generateFromChat`, `variations: 3`. Same DTO, same orchestrator, same flat result.

**The conversation is not a conversation.** `generations.service.ts:87` passes `undefined` for the context arg. `conversationId` is only an FK on the `Extraction` row. History is stored, titled, favorited, listed — and never read back into generation. Nobody noticed, because nothing depended on it.

**Edit and Use were byte-identical.** Both handlers built the same `Template`, called the same `onTemplateLoad`, and closed the panel. (Earlier in the session I said they differed by the `onClose()`; that was wrong — I had only read to line 1170 and missed the close at 1173.)

**The structured→prose→LLM→structured round-trip.** Quick Generate validates `address`/`price` client-side (`RightSidebar.tsx:376-388`), flattens them to a sentence via `buildPropertyPrompt` (`:256`), then the backend spends an LLM call re-parsing that sentence (`prompt-extractor.service.ts:40`) and **rejects if the LLM missed them** (`generations.service.ts:99`). Quick Generate can fail on data it is holding in memory. This is the real duplication — not the two UIs.

**Dead weight in the chat:** 1,595 lines, 26 components, 15 markdown files (three claiming finality), a 355-line `EnhancedSuggestionsPanel` rendered permanently `isOpen={false}`, `loadTestConversations` imported and never called, five orphaned components.

**Verdict (see §10 for the product call):** the chat holds two hostages — the only property-photo path (US-AI-010) and the only ungated free-text entry. That is the only reason it stays.

## 2. BL-24 — fixed and verified

`RightSidebar` set `showResults` only from the socket's `completed` event. A missed delivery left the CTA at "Starting…" forever while the server had finished — and the user's instinct is to regenerate, paying twice for a design they already own. A billing defect once revenue is on.

**Fix (authored by Dinesh, reviewed here):** REST status poll mirroring `AIChatBox` (2.5s, 80-poll ceiling), idempotent `terminalStateHandledRef`, `visibilitychange` re-check, and a notice pointing at My Designs on exhaustion rather than a dead CTA.

**One regression found and removed:** the poll wrote `setGenerationProgress(status.progress ?? 0)`, but `GET /:id/status` returns only `{ id, status, errorMessage }` — so progress reset to 0 and the label to "Generating…" every 2.5s, dragging the bar backwards on the path where the socket *works*. Optional fields mean `tsc` cannot catch it. The poll now owns terminal state only; the socket owns progress. `AIChatBox.checkStatusOnce` is the reference and behaves the same way.

**Tests:** `e2e/bl-24-quick-generate-poll.spec.ts`, 2 cases, green against localhost.

**Mutation-verified** — this is the part worth remembering:

| Mutation | TC-01 | TC-02 |
|---|---|---|
| Remove `terminalStateHandledRef.current = false` reset | ✅ passes | ❌ fails |

TC-01 is structurally blind to a stuck terminal guard, because the first generation always works. Shipping TC-01 alone would have let "BL-24 is fixed" through while every generation after the first still hung.

## 6. NEW P1 — production template gallery is empty

A new user signs up on production and sees **"No templates found matching your criteria."** That is the first screen after registration and the entry point to the editor.

**Root cause:** the gallery is entirely DB-driven. `starterCanvasTemplates.ts:56` is `export const STARTER_CANVAS_TEMPLATES: StarterCanvasTemplate[] = [];`

| Environment | admin-curated canvas templates |
|---|---|
| local dev | **5** |
| staging | **0** |
| production | **0** |

Red herring: `GET /api/v1/templates` returns 5 rows on production — those are the *generation-side* templates `selectBestTemplate` uses, a different concept. The gallery queries `/api/v1/canvas-templates`.

### ⚠ The two-script catch

`update-template-images.ts` **only updates existing rows** (`prisma.infographic.update`). With 0 templates on production it is a **no-op** and the gallery stays empty.

```bash
# from repo root, with that environment's DATABASE_URL
npx tsx api/scripts/seed-premium-templates.ts    # CREATES the 5 (aiModel: canvas-template, visibility: admin_curated)
npx tsx api/scripts/update-template-images.ts    # swaps SVG stubs for real photos
```

Both scripts are tracked and deployed (in `101fe14` since `1a74171`, 2026-08-21 — **17 days unrun**). `seed-premium-templates.ts` is documented idempotent.

**Stale comment to fix:** `update-template-images.ts` header claims `seed-premium-templates.ts` had its "source deleted in US-AI-037". It did not — the file is tracked, on disk, and deployed.

## 9. ⚠ The squash-merge trap — cost me two wrong conclusions

**Squash merges make merged branches look unmerged by SHA.** `git log main..branch` and `git cherry` both report the original commits as absent, because the squash rewrote them into one new commit.

This produced two false claims this session:
1. **In `/standup`:** "root cause located — the template seeding is stranded on unmerged branch `feat/plat/orion-0.6.0-upgrade`." It was not. Its content landed via `1a74171` (PR #34, 2026-08-21). The subsequent cherry-pick was an empty no-op.
2. **During branch cleanup:** `git diff main..branch -- $PATHS --stat` — everything after `--` is a *pathspec*, so `--stat` was swallowed as a filename and I read a truncated full diff as a stat. Also `git branch -d` succeeding proves little: it accepts a branch merged into its own *upstream*, trivially true for anything pushed.

**The check that actually works:** GitHub's merge records (`gh pr list --state merged --head <branch>`) plus `git merge-base --is-ancestor <mergeCommit> origin/main`.
